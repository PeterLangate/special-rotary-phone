Introduction

Chapter 1What FleetFlow is

FleetFlow (working name “Armada”) is a container-haulage management application for small haulage firms — an instegsprodukt (entry-level product) for små åkerier. It is the production successor to “C-Flow”, a Power Apps prototype that was never sold or implemented — so FleetFlow starts clean (no migration) and must far surpass that prototype on three fronts: look & feel, performance, and cost (no Power Apps license). Chapter 9 analyses the predecessor in detail.

The three goals that define the project

1 · Look & feel — far better

A bespoke, mobile-first interface under full design control and Langate branding — not generic, auto-generated Power Apps forms.

2 · Performance — snappy

Immediate load and immediate feedback on every interaction. The screen reacts in the same frame; the save confirms behind it.

3 · No Power Apps license

Built on SharePoint (included in Microsoft 365), not Power Apps + Dataverse, so there is no premium Power Platform licensing cost.

+ Multi-lingual

Every screen runs through Langate’s existing translation system — Swedish and English from day one, more languages with no code change.

What it manages

The domain is container / skip haulage: customers order containers (behållare — from 190 L bins to 40 m³ roll-off containers and compactors) delivered or collected (körningar, type Utkörning / Hämtning) at addresses, by drivers in trucks, with completion marks and vehicle telemetry. The full entity model is in Chapter 7.

Who uses it

Office / dispatch

Manages customers, contacts, addresses, vehicles, drivers and container types, and creates and assigns körningar. Desktop or tablet.

Drivers

See today’s jobs (Vart ska jag köra idag) and their own list (Mina körningar), and mark jobs complete — phone-first. New vs C-Flow.

Architecture overview

Chapter 2The big picture

FleetFlow does not start from scratch. It reuses the proven shape of two existing Langate solutions: the ISO certification tool (SharePoint front-end + Azure Function backend + dynamic list provisioning) and Rollcall (a lean, mobile-first classic SharePoint page).

A two-part cooperating system

The product is two halves that work together, both must be running:

1 · SharePoint browser app

A webpack bundle that renders the UI, reads and writes SharePoint list data, and asks the backend to provision the site. Does no privileged or long-running work itself.

2 · Azure Function (Node)

Runs under an app-only identity with Full Control. Owns dynamic list provisioning and background work such as telemetry ingestion.

What we reuse, and why

ConcernReused fromBenefit
Front-end host & bootstrapRollcallMobile-first classic page, proven on phones
Backend + provisioningISOSelf-provisioning sites, no manual setup
Shared k* librariesAdmin (ReUsableTS)HTTP, CRUD, dates, errors already solved
Single-version buildISOServer & client can never drift apart

What we deliberately leave behind

No question-catalog or wizard. ISO is a question-driven tool with a large catalog/wizard subsystem. FleetFlow is conventional CRUD (orders, trucks, drivers, routes), so that machinery is dropped. We keep the data-model shape — domain objects that own their own persistence — not the catalog.

The chapters that follow take each layer in turn: the front-end host (Ch. 3), the backend (Ch. 4), dynamic provisioning (Ch. 5), the shared libraries (Ch. 6), the domain model (Ch. 7), and telemetry (Ch. 8). Chapter 9 compares FleetFlow against the C-Flow prototype goal by goal; Chapter 10 maps the wider market and how the schema generalises; and Chapter 11 records the decisions taken and the questions still open.

Chapter 3Front-end host & UI

The webpack bundle is the product; the SharePoint host that loads it is a thin shim. The same bundle can run under three hosts — only the start-up call differs. That is what makes “sandboxed now, SPFx later” cheap.

One bundle, three hosts

Classic page / sandboxed WSP nowA ScriptLink on a classic pageStartGetBaseInfo
SPFx Application Customizer laterAn extension injects the script on every modern pageSPFXGetBaseInfo(context)

Boot is keyed off the application type, so converting to SPFx is a pure add-on, not a rewrite. ISO already ships the minimal SPFx customizer this conversion would use.

Mobile-first, modelled on Rollcall

The driver surface follows Rollcall’s recipe, proven on phone browsers:

  • A classic SharePoint page that strips all SharePoint chrome (suite bar, title row, ribbon, navigation) for a full-bleed app surface.
  • A single mount point; the app builds its own UI into it.
  • Large touch targets and a glanceable layout for drivers in the cab.
  • Shared mobile-styled notifications and continuous, visible feedback on every tap.
  • A Langate-branded “frosted glass” finish — the deep-blue primary, the signature green accent and DM Sans — rendered as translucent panels over a soft brand backdrop, with WCAG AA-contrast colour throughout.
Why Rollcall, not the ISO wizard: Rollcall is a thin, single-page mobile app — a much closer fit to a driver’s “what do I drive today” view than ISO’s multi-view desktop wizard.

Front-end

Owner & admin: a responsive desktop console

The dispatcher and owner surfaces are the mirror of the driver app — a desktop console that is fully responsive: the dashboard, live vehicle map, schedule and data grids fill the available width on a wide monitor (the map grows to dominate the screen) and reflow gracefully down to a tablet, rather than sitting in a fixed narrow column. The same Langate “frosted glass” finish carries across both apps.

The dashboard is now a start-of-day cockpit that answers one question — “what needs me right now?” A short quick-action bar puts the day’s highest-value moves one click away (assign the queue, open the schedule, open the worklists), and a priority card pulls the single most urgent thing to the very top. A row of attention tiles counts everything that needs a dispatcher’s eye (jobs with no driver, overdue runs, load-fit conflicts, vehicles in the workshop, containers left on site, open incident reports); each tile jumps straight to that worklist and, once the app has been used for a few days, carries a small trend line showing whether that number is climbing or falling. Below, today’s jobs are shown as a completion donut beside a status breakdown with a “stops completed today” progress bar; a live map previews where the fleet is right now; and the fleet panel shows every vehicle at a glance, colour-coded by status. Alongside, three separate panels — one per time frame show what is running now, what is running late and the next few departures (that last one carrying a one-click link to the full day’s schedule), and a latest-activity feed streams the newest events. Every panel links straight into the tab that owns the action — the dashboard points, the specialist tabs do.

Drivers, locations and container types now have their own detail views — a driver’s assigned vehicles, certifications and jobs; a location’s coordinates and the jobs that stop there; a container type’s compatible vehicles and the jobs that need it — each cross-linked so you can hop from one to the next. A route’s activity timeline is expandable (tap an event to see exactly when it happened, on which stop, and its detail), and a completed drive’s proof-of-delivery PDF can be downloaded or previewed straight from the route. The turn-by-turn navigator now shades its route by live traffic (green→red) and shows lane guidance at the roads that carry it.

The admin detail modals are editable forms, not read-only reports: a vehicle, customer or route can be changed in place (assignments, stops, contacts) and saved through the same optimistic writer that powers the grids. Creating a new drive and editing an existing one use the same form — identical two-column layout, container-fit check and stops grid — so the two never drift apart.

The drive dialog was redesigned so a run’s status has a single home and every completion or pause is truthful. A drive’s status is no longer a hand-picked dropdown that could disagree with its stops; it is a read-only badge and a “stops done” progress bar at the top of the dialog, derived from the stops themselves, alongside the only status actions — Complete drive and Pause. Completing a drive from the office opens a plain-spoken confirmation that lists exactly which stops it will finish and records them honestly as an office completion (a clear “Office” proof marker, never a fabricated GPS position, and it leaves each stop’s instructions intact) — so a dispatcher can always tell a field-verified stop from a desk one. Pausing a drive now asks why (a quick reason, with common presets), stamps who and when, shows a banner on the drive explaining the hold, and records the pause, resume and completion on the drive’s activity timeline — a real audit trail.

The jobs list stays fast at scale: once a fleet holds more than 75 drives it pages the grid (Previous / “Page X of Y” / Next, newest first) instead of drawing one endless table, so the console loads quickly and stays easy to scan; a small fleet still shows every drive in a single list. The driver app remains mobile-first, but on a desktop browser it widens into a roomier layout with route cards in a grid. While a drive is in progress the live map is the primary surface: the detail goes edge-to-edge, with the customer, instructions and stops in a slim column on the left and the map filling the entire rest of the screen — the same “the map dominates the monitor” principle as the admin console, so nothing is wasted on a wide screen.

Places are edited on a map, not in raw number boxes. The Locations grid carries a single “Location” column that opens an interactive Mapbox map picker: start typing an address and a live list of suggestions appears — pick one and the pin and coordinates drop in for you — or click / drag the pin to place it exactly where the site is, and the coordinates fill in automatically (they can still be typed by hand for precision). It is one reusable building block — the same map-picker column can be dropped into any future grid that needs a point on the map — so capturing a depot, customer site or drop-off is a glance-and-click instead of guessing latitude and longitude.

Because that map picker is a reusable building block, it also powers a “+ New location” option right next to every stop’s location field — on the driver’s New drive form and on the admin drive form alike. If the place a driver or dispatcher needs isn’t in the list yet, they pin it on the map right there, name it and set its type, and it is created and selected on the spot — no detour to a separate Locations screen first.

Front-end

The live vehicle map

On the live vehicle map each vehicle is drawn as a truck marker — a compact rounded pin carrying a bold truck silhouette, coloured by its status (green driving, slate idle, amber on-hold, red needs attention) — so the fleet reads at a glance as trucks rather than abstract dots, crisp and legible even zoomed out to a whole country. Each truck also carries a small caption above it showing its registration plate and the driver’s name, so a dispatcher sees not just where a truck is but which one and who is driving it, without clicking. Clicking a truck opens a card listing all of that truck’s drives for the day — each showing the customer, the status, the departure time and how many stops are done. Every drive in the card is a link: click it to open that drive’s full details. Each also has a share button that produces a customer tracking link, so a haulier can tell a customer “your container is on the way” straight from the map. (A completed drive now correctly reads 2 of 2 stops done, not the earlier confusing 0 of 2.) The map opens clean, showing only the fleet; the day’s job stops are an optional layer, off by default and turned on with a “Show stops” switch in the map’s options menu when the dispatcher wants to see where the work is. Alongside it a “Traffic” switch overlays live road congestion (green flowing through to red for a jam), so the dispatcher can see at a glance which routes are slow. And each truck’s trail of where it has actually driven today is snapped to the roads — the raw GPS breadcrumb is cleaned up so the path follows the streets instead of wandering across buildings.

A “Show locations” switch (in the same options menu, off by default) marks every one of the fleet’s sites — depots, customer premises, ports, rest stops — with a distinct white house symbol whose roof is colour-coded by kind (so a depot, a customer site and any other place read apart at a glance, and the bright house stays legible on both the light and the dark map). Clicking a house opens a small card suggesting what to do there: View details opens that site’s full record, and Nearest truck finds the closest vehicle that can actually take the job and draws the route to it — so a dispatcher can act on a place straight from the map.

The map also has a “Simulate day” button that plays the whole fleet’s day out in about twenty seconds: every truck sets off from the start of its route and glides smoothly along the real roads it drives — motorways and A-roads, not straight lines across country — laying down its route ahead of it and its progress behind, with the view automatically framed so the entire day stays on screen. When it finishes, a replay slider lets you scrub back and forth to any moment of the day.

When a new job comes in, you can find the right truck for it straight from the map. Type an address into the search box at the top — FleetFlow flies there and drops a pin on the exact spot, with two choices in its pop-up. “Nearest truck” finds the closest vehicle that can actually carry the load (not just the closest one) and draws a traffic-coloured line to it. “Add location” saves that spot as a new customer or site in one step, with its name already filled in. So the “which truck is nearest?” answer is now for a place you pick, not a fixed guess. And once you have saved a spot, its pin stays on the map and stays clickable — click it again any time to find the nearest truck to that saved site.

Front-end

Every screen has a link, and Back just works

FleetFlow is a single-page app, but it behaves like the web you expect. Every screen has its own address in the browser bar — the driver’s drives list, a specific drive, the admin dashboard, the schedule, any admin tab — so a link can be bookmarked or shared and opens straight onto that screen. And the browser’s Back and Forward buttons work: Back steps to the previous screen inside the app (a drive back to the list, one admin tab back to the last, an app back to the home chooser) instead of jumping out of FleetFlow entirely. The links go one level deeper too — a specific Configuration section or an Operations worklist has its own address, so Back walks back through those as well. It is one consistent behaviour whether you click a card, click an admin tab, or press Back — the address bar and the on-screen view always agree.

Back also closes an open pop-up. When a detail form or the driver’s incident report is on screen, pressing Back simply closes it and returns you to exactly where you were — the natural gesture, especially on a phone — rather than jumping away underneath it. A bookmarked link never re-opens a pop-up (it opens the screen behind it); pop-ups belong to the moment, not to a shareable address.

Under the hood this is a small, reusable building block in the shared library, so the same “every screen has a link and Back just works” behaviour can be switched on for any of Langate’s single-page apps, not just FleetFlow.

Help is one hover (or long-press) away

Every button, tab, toggle and form field that could use an explanation carries a short help note in the current language. On the desktop admin console it appears when you hover the control (or tab to it with the keyboard); on the phone driver app — where a plain hover tooltip never shows — you press and hold to reveal it. So a control such as “Pausa” on a drive is no longer a guess: hold it and it explains “pauses the drive — it leaves active dispatch and can be resumed later.” The notes are translated the same way as the rest of the interface (Swedish, English, German), so they always match the language a person is working in.

It is one small, reusable component: a single tidy help bubble, styled to match the rest of the app, that any control can opt into with one line — so the coverage can grow without adding clutter, and the same help layer is available to Langate’s other apps.

Backend

Chapter 4The Azure Function backend

The backend is a Node.js Azure Function that owns everything privileged: provisioning SharePoint lists, and background work such as telemetry ingestion. It runs under an app-only identity with Full Control, so it can act regardless of who is signed in.

What it does

  • HTTP endpoints the browser calls — chiefly a “make sure the site is set up” endpoint the bundle kicks on load.
  • Timer-triggered workers for background jobs, following ISO’s scanner / worker pattern.
  • Central error reporting — the function arms its own global error handler so server errors are surfaced, never silently swallowed.

One Function per customer, in their own subscription

Decided 2026-06-25: each fleet manager (customer) runs their own Azure Function in their own Azure subscription — not a shared vendor-hosted service. The function, its secrets, and its access grant all live inside the customer’s subscription.

This is the ISO single-tenant-per-customer model, taken one step further. The browser bundle for each customer points at that customer’s own Function endpoint. The consequences for build, deployment, and configuration are covered in Chapters 5 and 11.

Why a backend at all

Two jobs genuinely need server-side power. First, provisioning: creating SharePoint lists and columns requires elevated rights a normal user may not have — the app-only identity lets any user’s first page load fully set up the site (Chapter 5). Second, telemetry: pulling vehicle position data and writing it to storage is background work that must run without a user present (Chapter 8).

Provisioning

Chapter 5Dynamic SharePoint setup

FleetFlow describes the SharePoint lists, columns, and permissions it needs in a single declarative schema, and lets the Azure Function build them. There is no manual list setup and no separate install step for the data structure.

How it works

  1. The schema (one JSON file) describes every list, column, folder, and permission set.
  2. The browser bundle, on load, asks the function to ensure the site matches the schema.
  3. The function reads the schema and creates anything missing — lists, columns, folders, permissions.
  4. The bundle polls until the site is fully set up, then loads its data.

Two properties that matter

Idempotent

A version stamp means repeat runs are cheap. Adding a column is just an edit to the schema plus a version bump; the function adds whatever it does not already find.

Order-safe

Any data read that needs a new column waits until provisioning reports done — so a read can never ask for a column the function has not created yet.

Onboarding a customer

Because each customer is self-hosted (Chapter 4), provisioning has two parts: a one-time onboarding step (create the site, grant the function access, register the bundle) and the per-load schema convergence above, which keeps an existing site up to date automatically.

Reused wholesale. The schema-to-lists engine is shared library code already proven in ISO. FleetFlow supplies its own schema; the engine that applies it is not rewritten.

Shared libraries

Chapter 6The shared k* libraries

FleetFlow does not hand-roll networking, persistence, dates, translations, or error handling. Langate’s shared k* libraries already solve these, and the same code runs in both halves of the system — the Azure Function and the browser.

One core, two faces

The libraries are built as an environment-neutral core consumed by both the Node.js function and the browser. The browser classes are thin shells over that shared core, so a list read, a CRUD save, or a permission apply behaves identically on the server and the client.

What is already solved

ConcernUse the shared
HTTP to SharePoint / GraphREST helper (retries, request digest, 429 handling)
List item create / read / updateItem + typed-collection classes
Files & librariesFile upload / download helpers
Lists, views, schema, permissionsList / schema / permission engine
Dates & timesCulture-aware time helpers
TranslationsPhrase database + localization class
ErrorsCentral error handler — handled or reported, never hidden
Reuse before writing. Before any networking, persistence, or framework-utility code is written, the shared libraries are searched first. If a shared method almost fits, it is extended with a defaulted parameter rather than duplicated — and bugs are fixed in the shared library directly, never worked around locally.

Multi-lingual & versioning

Every user-facing string is multi-lingual. Text comes from Langate’s shared phrase database (generated, never hand-edited) — Swedish and English from day one, with more languages addable and no code change. (C-Flow was Swedish-only.) A single generated version file is imported by both halves, so every error report carries the exact build — the server and client can never disagree about which version is running.

Domain model

Vehicle constraints & fit

C-Flow was built for a container company, where each container size fits only some trucks. FleetFlow makes this a first-class, typed model: a Fordon carries its constraints — max weight, dimensions, passenger capacity, and which container sizes it can take — and a Behållare carries the matching requirement. Assigning a load to a truck is checked against these constraints, so dispatch only offers trucks that actually fit. The same model generalises the product beyond containers — for example passenger capacity for taxi-type work.

A körning’s life

Created → Assigned → En route → Completed. The dispatcher creates and assigns; the driver drives and completes. A single authority decides which transitions are legal, so every screen agrees and the audit trail (who, when, where) stays consistent. Completing a körning creates a separate completion record with the captured location.
Relationships are lightweight. Entities reference each other by simple stable IDs resolved in memory — the convention proven in ISO — not heavy cross-list lookups. Final columns and the work-order-to-körning cardinality are confirmed in detailed design (Chapter 11).
Every drive is scheduled to the minute. A körning is stored with a full date and time for its departure and its arrival, and each stop carries its own planned time (and, once the driver completes it, the actual time) — so the driver app, the dispatch board and the customer ETA all show when, not just which day.

Telemetry

Chapter 8Vehicle telemetry

Trucks and transported goods carry GPS sensors, OBD2 connectors, and utility boxes that report position and status. FleetFlow ingests that stream in the background and stores it so the office can see “var är mina bilar” — where are my vehicles.

Where the data lands — decided

Decided 2026-06-25: telemetry is stored as files in SharePoint, not as list rows. One document library per vehicle; inside it, one folder per month; inside that, one JSON file per day holding that day’s log. The day’s file is over-written on each data receipt, and version history is turned off on these libraries so the rewrites do not pile up versions.

Why files, not list rows

A single truck reporting every few seconds produces thousands of points per day. Writing one SharePoint list row per point would quickly throttle the service and overwhelm list views. A per-day JSON file sidesteps both limits and keeps everything inside SharePoint — no extra cloud database to operate.

Telemetry

What lands in each daily file

One JSON file per vehicle per day (inside a month folder), over-written on each receipt — the whole day’s fixes in one place. Short keys keep a multi-thousand-fix day small.

{
  "v": 1,                          // schema version
  "regNr": "ABC123",
  "date": "2026-06-25",            // fleet-local day
  "tz": "Europe/Stockholm",
  "source": "flespi",              // vendor platform
  "fixCount": 1234,
  "fixes": [
    { "t": "2026-06-25T07:14:32Z", // UTC time
      "lat": 55.6050, "lng": 13.0038,
      "spd": 52.3,                 // km per hour
      "ign": true,                 // ignition  (OBD2 only)
      "fuel": 64.5,                // percent   (OBD2 only)
      "odo": 154233 }              // km        (OBD2 only)
  ]
}
  • UTC stored, local shown. Times are stored in UTC; the app displays Swedish time.
  • Optional fields. A bare GPS tag sends only time + position; OBD2 / utility units add ignition, fuel, mileage and fault codes.
  • Live map. Reads the last fix of today’s file per vehicle; history reads whole day files across a date range.
Privacy by design — automatic. The per-customer Azure Function purges telemetry files older than the retention window (e.g. 90 days) on a timer — no manual cleanup. Live positions are dispatcher-only; one driver never sees another’s position.

Chapter 9Replacing C-Flow

FleetFlow is the production successor to “C-Flow”, a Power Apps model-driven prototype on Dataverse that was never sold or implemented. It exists only as a prototype, and its value here is as a worked reference for the domain. FleetFlow must far surpass it on three goals — and adds capabilities C-Flow never had.

What C-Flow is

An office / dispatch CRUD prototype for a container company: customers, contacts, addresses, container types, vehicles, drivers, and körningar. It is a standard Microsoft model-driven app — generic chrome, dense toolbars, auto-generated forms, Swedish only. The purple “Begränsat läge” (Limited mode) banner in the screenshots simply marks it as a prototype. Reference shots: PowerVersionScreenshots/.

Never deployed. Because C-Flow was never sold or implemented, there is no data to migrate and no cutover — FleetFlow starts clean.

Build container-first, stay market-ready. The container schema (Chapter 7) is one projection of this generic spine. Storage backends

Chapter 12Storage backends & deployment options

FleetFlow treats the database as a choice, not a commitment. Behind a single storage seam, the very same product — every screen and every feature — runs unchanged on any of three Microsoft-ecosystem backends: the browser’s own store, SharePoint lists, or Dataverse. This chapter states that guarantee and weighs the trade-offs, so each customer can pick the option that fits their scale, budget, and governance.

The same product on any backend

A thin data layer sits between the application and wherever the records physically live. Everything above that layer — the driver app, the owner live-map, dispatch, incidents, reporting — speaks one neutral record format and never talks to a specific database directly. Swapping the backend therefore changes only where the data is stored, never what the app can do.

Full functionality on all three. The driver app, the owner live-map, dispatch and scheduling, incident reporting, proof-of-delivery, the printable reports, and vehicle telemetry all work identically whether the data lives in the browser, in SharePoint, or in Dataverse. Choosing a backend is a decision about operations, scale, and cost — never about features.

Because the selection happens at run time, a single browser build can be pointed at any of the three. Moving from a local pilot to a shared production database is a configuration change, not a rewrite.

Storage backends

The three options

In-browser database. The local-first store the prototype ships today. Data lives inside the browser on the device, seeded and integrity-checked on load. It needs no server, no account, and no network — ideal for demonstrations, pilots, and offline single-user use.

SharePoint lists. The fleet’s data as ordinary SharePoint lists inside the customer’s own Microsoft 365 tenant, created automatically on first use. It is included in the Microsoft 365 the customer already pays for, shared across the whole team, and governed by the familiar SharePoint permission, backup, and retention model.

Dataverse. The Power Platform’s relational business database. It offers true tables, relationships, and enterprise-grade security and scale — the right home for very large fleets or for customers already invested in Dynamics 365 and the Power Platform.

Strengths and trade-offs

BackendStrengthsTrade-offs
In-browser Zero infrastructure and zero cost; instant, snappy performance because everything is local; works fully offline; nothing to provision. Data lives only in that one browser on that one device — not shared, not centrally backed up, and cleared if the browser storage is reset. Not intended for shared production operations.
SharePoint lists No extra license — included in Microsoft 365 (a core project goal); data stays in the customer’s own tenant under their governance, permissions, and backup; shared across the team; provisioned automatically; reuses Langate’s proven SharePoint building blocks. Very large lists need care (paging and view limits); it is a list store, not a relational database, so cross-references are resolved by the app; attachments use a document library; and remote writes need network-resilience handling.
Dataverse A true relational database with native relationships, keys, and a rich security model; comfortable at very large scale; strong for complex reporting and integration; a natural fit where Dynamics 365 / Power Platform is already in use. Reintroduces a Power Platform license cost — the very expense the “no Power Apps license” goal set out to avoid; more setup; and net-new integration work. Usually more than a small fleet needs.
How to choose. Start in the browser for demos, pilots, and evaluation. For the great majority of production fleets, run on SharePoint lists — it keeps the “no extra license” promise and puts the data in the customer’s own Microsoft 365. Choose Dataverse when a customer already lives in the Power Platform, or when fleet size and reporting demands justify an enterprise relational database.
One product, three homes. Whichever backend a customer picks, they get the complete FleetFlow — and because the choice sits behind the storage seam, they can start local, grow into SharePoint, and move up to Dataverse without changing the app.
