Overview

Chapter 1What Sentinel watches, and how it tells you

CTS Sentinel is the always-on companion to the Core Tenant Security dashboard. Where the dashboard is something an admin opens, Sentinel is an Azure Function that runs on a schedule, applies the same detection logic server-side, and pushes a notification the moment something worth knowing happens. This chapter explains the severity model and how notifications are delivered; the rest of the book is the event catalogue.

The same detections, server-side

Sentinel does not re-invent the analysis. It reuses the dashboard’s detection modules unchanged — impossible-travel geometry, the spray-that-succeeded correlator, the Entra risk classifier, and the per-user baseline — so an alert you receive by email means exactly what the same finding means on the dashboard. The only new parts are when it runs (a timer, plus near-real-time Microsoft Graph subscriptions) and how it reaches you.

How notifications are delivered

Sentinel keeps its own delivery deliberately simple. It does not send mail itself. Instead, every finding is written as a row to a SharePoint list, CTS Sentinel Notifications, and a Power Automate flow watches that list and fans the row out to the right channels — e-mail from a shared mailbox, a Teams message, or a webhook.

Why this design: the Function already writes to SharePoint lists (it shares the dashboard’s lists), so appending a notification row needs no new permission and no mail credential. Power Automate’s built-in connectors handle the actual send — one place to change the recipient list, the wording, or the channel, with no redeploy of the Function.
Severity Delivered as
CriticalImmediate — e-mail and Teams, plus a webhook to the SIEM. The "act now" tier.
HighImmediate — e-mail and Teams.
MediumBatched into an hourly summary so a busy signal doesn’t become noise.
InfoRolled into the daily digest only.

A watchlist of VIP users, sensitive applications, and privileged roles raises any matching finding by one severity level — so a new-country sign-in is informational for most people but high for a Global Administrator.

No duplicate alerts

Sentinel keeps a notified-id ledger. Each finding has a stable key — a sign-in event id, an incident id, or a composite such as IP·user·hour — and once a key has been notified it is never notified again. A poll that re-reads an unchanged window therefore sends zero notifications. This is what makes a five-minute timer safe.

Chapter 4Network, infrastructure & digest

The events that only a server-side companion can produce: threat-intel enrichment that needs a secret the browser can’t hold, an optional bridge to physical network gear, Sentinel’s own health, and the scheduled digest.

Sign-in from a threat-feed IPThreat-intel enrichmentHighServer-side enrichment matched the source IP to a Tor / malicious / bad-ASN feed. Dedup: UPN · IP · day.

UniFi / Ubiquiti event OptionalUniFi clientMediumAn IDS/IPS alarm, a new device on the LAN, a firewall-rule change, or a DPI anomaly — routed through the same notifier. High on an IDS hit.
Monitor healthSelf-checkInfoA missed run, sustained Graph throttling, or an auth failure; high when Sentinel itself is degraded.
Why this lane is server-only. A paid threat-intel feed’s API key cannot ship inside a browser bundle, and a SharePoint page’s content policy blocks calls to unknown origins. Sentinel holds the key server-side and enriches every sign-in IP — then writes the verdict back where the dashboard can show it.

One row, many channels. Every event in this book — identity, Defender, directory, network, digest — reaches you the same way: Sentinel writes a row to the CTS Sentinel Notifications list, and a Power Automate flow sends it on as e-mail from the shared mailbox, a Teams message, or a webhook. Change a recipient or reword an alert in the flow, not in the Function.
