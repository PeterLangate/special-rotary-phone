Chapter 1 · Overview

Chapter 1One tool, many standards, three axes

The certification tool manages any Annex SL ISO management-system standard — 27001:2022 first, then 9001, 14001, 22301, 27701, 45001 as they are added. Every standard reuses the same schema, the same list pattern, the same column set. Adding a standard is data, not design. This document is the operating picture: how the lists are structured, who can see what, who answers what, and how the SPFx app provisions and runs the whole thing.

Three axes

Everything in this document maps to one of three orthogonal axes. Keep them straight when reading the rest of the chapters.

AxisUnitMechanismWhere to read it

Read Per list SharePoint group permissions, broken inheritance Ch 7 (groups) · Ch 8 (read & write matrix)
Answer Per question (with per-row variants for risk register, training records) ISOwnerRole column on every item, optionally overridden by a per-item ISCurrentAssignee person Ch 9 (owner roles) · Ch 10 (reassignment)

Chapter 2Lists, libraries & naming

Each standard provisions a fixed set of SharePoint lists and one document library. The names follow a single pattern — {slug}_{listShortName} — so cross-standard tooling can find any list by string substitution.

2.1 The naming pattern

Every list and library is prefixed with the standard slug followed by an underscore. The slug substitution is the only variable; the short name on the right is identical across every standard.

PatternExample (27001)Example (9001)
{slug}_{listShortName}27001_5_Leadership9001_5_Leadership
{slug}_Evidence27001-Evidence9001_Evidence
SharePoint character rules
Underscores read cleanly in SharePoint URLs and survive both the internal name and the display name unchanged. Avoid spaces (encoded as %20) and dashes (the URL converts them to underscores anyway).

3.3 Why a JSON payload instead of per-answerType columns

The catalog has ten answerTypes (shortText, freeText, boolean, singleChoice, multiChoice, date, numeric, personRef, documentRef, list). A column-per-type design would either require nullable columns of every type on every list, or a per-list schema variant. Both fight SharePoint's schema model.

Instead, the answer is stored as JSON in ISAnswerJson. The SPFx app reads the question's answerType from the catalog and renders the right control for the type. SharePoint sees a single multi-line note column on every list, so the schema is uniform.

Don't filter on the JSON
ISAnswerJson is a Note column, so it cannot be added as an Indexed Column and cannot be filtered reliably via the list REST API ($filter on a Note column is not first-class and fails on lists past the view threshold). All typed filtering — by status, assignee, answered date — must go through the dedicated columns (ISStatus, ISAnsweredBy, ISAnsweredDate), which are indexable. SharePoint Search will crawl the Note content into the search index, but JSON-aware queries (e.g. "status=Submitted inside the JSON") are not possible at the list level — that's why ISStatus exists as its own Choice column.

Chapter 4 · Evidence library

Chapter 4The evidence document library

One document library per standard — {slug}_Evidence — holds every file referenced by a documentRef answer. The library is partitioned into one permission-area folder per question list, and every upload is mediated by the iso-cert-tool app — no end user, invited or staff, gets Add rights on the library directly. Files are linked from the answer row by URL (ISEvidenceLink); the library carries extra metadata so the SPFx app and auditors can find and assess files without opening the parent list.

4.1 Why a library, not an attachment

One file, many references

A single policy document (e.g. the Information Security Policy) is the evidence for multiple catalog questions (5.2 e, A.5.1, parts of A.5.4). Putting it in a library lets all questions link the same file; attachments would duplicate it per row.

Versioning & approval

Document libraries get version history, approval workflows, check-out/check-in, and content-type metadata for free. Item attachments do not.

External-auditor access

Auditors typically get read access to the library — they sample documents directly without needing access to the answer lists (which carry the gaps and weaknesses).

Retention & legal hold

SharePoint retention labels work cleanly on libraries. ISO 27001 clause 7.5 requires document retention and disposition — the library is the natural enforcement point.

Chapter 4 · Evidence library

4.3 Uploading and linking a file — app-mediated

No end user holds Add rights on the Evidence library. When a user attaches a document to a documentRef question, the SPFx app does not write to the library itself — it streams the file to the iso-cert-tool app's evidence-upload endpoint, which performs the write as the app identity:

  1. The SPFx front-end streams the file bytes (plus the question id and an optional ISDocType) to the iso-cert-tool upload endpoint.
  2. The app resolves the question's permission area from (StandardSlug, area) and locates the matching permission-area folder. The 11 area folders and their ACLs are provisioned once by the permission-provisioning script (Chapter 8); the app verifies the folder exists and rejects the upload if it does not.
  3. The app uploads the file into the area folder via the SharePoint REST API (Files/add) as the app identity, then stamps ISLinkedQuestionId, ISDocumentOwner, ISEvidenceArea and ISDocType with a follow-up MERGE on the file's list item.
  4. The app returns the resulting ServerRelativeUrl; the SPFx app writes it into the answer row's ISEvidenceLink column.
Many-to-many references
A document can evidence several questions. The file lives physically in one permission-area folder — the area of its primary ISLinkedQuestionId. Secondary references are tracked by other answer rows pointing at the same library URL via ISEvidenceLink. Consequence: a reader who can see a secondary-area question but not the file's primary-area folder will see a link they cannot open. This is the single-source-of-truth trade-off; the SPFx UI shows a non-blocking “you may not have access to this linked file” note rather than a broken link.

4.4 Permission-area folders

The library is partitioned into one folder per question list — the folder is the permission boundary for evidence. Role inheritance is broken once per folder, and each folder's ACL is the read projection of that area's row in the Chapter 8 read matrix: every group with Read, Contribute or Full Control on the matching question list gets Read on the folder; every other group gets nothing. Folders never grant Contribute — all writes go through the app. A file uploaded into a folder inherits the folder ACL, so ~11 unique permission scopes per standard cover the whole library, far under SharePoint's limits.

The former physical folders (/Policies, /Procedures, /Registers, /Records, /SoA) are gone — the folder dimension is needed for permission areas. Document type moves to the ISDocType choice column; library views filter and group by it to give the same navigation without occupying the folder structure.
Migration of pre-existing evidence
Evidence uploaded under the old flat model keeps the old blanket library ACL until it is re-filed. The build order includes an explicit Evidence migration step: move each file into its area folder, set ISDocType from the old folder name, then verify the old folders are empty before removing them. Re-filing is a security fix, not just tidiness.

Escape hatch: if a single question ever needs evidence locked tighter than its whole area, a sub-folder with its own broken inheritance can be created under the area folder. Documented here; not provisioned by default.

Chapter 6How the lists get created

All lists, libraries and columns are provisioned at SPFx app startup, not by a separate admin script. The flow is idempotent: every run reads the current site state, compares it against the canonical kJSSchema, and creates only what is missing.

6.1 The three-step chain

  1. The per-standard generator (tools/generate-27001.mjs) emits data/sharepoint-27001.json in kJSSchema format — the same format consumed by the shared kSchemaToSPList helper.

The tool runs as two cooperating parts. Both must be running for a full setup to complete:

PartWhat it does at start-up

Why nothing loads before provisioning finishes
The app waits for provisioning to finish before it reads any data. This matters on an existing site that is being upgraded: if a read ran before a newly-added column existed, it would fail and stall the very step that adds the column. So the rule is simple — create/repair the columns first, read second.
Zero documents after setup is a fault, not "still working"
If you finish first-use (or example data) and the Documents library has no PDFs, the document-generator half is not running or could not be reached — the requests are sitting in ISO-RegenRequests with status Pending. That is a fault to investigate (is the Azure Function running?), never a normal end state. Locally, the generator is the func host on port 7078 (cd iso-cert-tool; npm start); in production it is the deployed Function App.

Chapter 7SharePoint Groups

The tool is designed for integrated management systems: one tenant, one SharePoint site, one set of cross-cutting groups, and as many standard catalogs as the organisation certifies against. Most groups are shared across every standard — only specialist roles that have no analogue outside a given standard get their own group. Names in SharePoint vs names in this document
SharePoint stores the group names with an ASCII hyphen (e.g. ISO - HR) and the literal word and instead of an ampersand (e.g. ISO - IT and SecOps, ISO 27001 - Dev and AppSec). The em dash in headings and the ampersand in prose are document-style only — they never reach SharePoint. The reason: the coding-powershell skill bans em dash inside PS1 files (PowerShell 5.1 truncates strings at it), and an ampersand inside a group name URL-encodes in REST calls and CSV exports in ways that surprise scripts downstream.

Reassignment flow

The “Reassign” action is visible only to the user named in ISCurrentAssignee and to ISO - Core Team. The flow runs through the Sites.Selected tenant app (see Chapter 12) — the user never has SP permission to change item permissions themselves.

  1. User clicks Reassign on a question.
  2. The in-house people picker opens. It filters internal users only (UPN suffix match on the tenant domain, or an AAD-group membership check).
  3. User picks the reassignee and optionally types an AssignmentNote (max 250 chars).
  4. The SPFx web part calls the reassignment endpoint exposed by the Sites.Selected app with the item id, the reassignee’s UPN, and the note.
  5. The app, running with site-scoped Full Control, performs steps 6 → 11 atomically (using a transaction wrapper that reverts the people-picker change if any sub-step fails).
  6. Ensure the reassignee is in ISO - Question Assignees via POST _api/web/sitegroups(<id>)/users — idempotent, no-op if already a member.
  7. Break inheritance on the list item with BreakRoleInheritance(copyRoleAssignments=false, clearSubscopes=false) — skipped if already broken.
  8. Grant the reassignee Contribute on the item.
  9. Grant the role-group that (ISStandardSlug, ISOwnerRole) resolves to in ISO-RoleMap Read on the item, and keep ISO - Core Team Full Control. The original team still sees the item read-only so they can monitor progress.
  10. Update fields: ISCurrentAssignee, ISAssignedAt, ISAssignedBy, ISAssignmentNote; append one line to ISAssignmentChain. SP versioning captures this as a single version.
  11. Append a row to ISO-AssignmentLog (see Chapter 11) and queue a notification row in the ISO-Outbox list — a Power Automate flow picks it up and sends it to the new and previous assignee from the shared mailbox.

An invited person owns a question item but holds no permission on the Evidence library (Chapter 8, Matrix C). When they attach proof to their question, the upload is mediated entirely by the iso-cert-tool app — this is a separate endpoint from the atomic reassignment transaction above:

  1. In their question form, the invited person picks a file and (optionally) a document type. The SPFx web part streams the bytes to the iso-cert-tool evidence-upload endpoint.
  2. The app verifies the caller is the question’s ISCurrentAssignee (or ISO - Core Team) — an invited person can only add evidence to a question they currently hold.

Why Sites.Selected, not Sites.FullControl.All

Sites.FullControl.All would grant the app write everywhere in the tenant — a single compromised credential could touch every SharePoint site. Sites.Selected grants nothing by default; an admin then runs one PATCH per site that needs access. The ISO 27001 site is the only site in the grant list. If the app is later extended to handle 9001, 14001, or 22301 catalogs, each new site gets its own grant.

Mail via the ISO-Outbox list — no Graph, no mailbox grant

The app sends no mail itself. To notify someone it writes a Pending row to the shared ISO-Outbox list (Chapter 11) via the SharePoint REST API. A Power Automate flow triggered on item creation sends the message from iso-noreply@langate.se — a shared mailbox dedicated to the tool — and flips the row to Sent or Failed. Reassignment notifications, weekly digests, and external-auditor invitations all flow through this one list.

This is deliberately the simplest design that works: the app needs no Microsoft Graph permission and no Exchange mailbox grant. The only credential with send rights is the Power Automate flow's connection — held by the flow, not the app. Even if the app certificate were stolen, no mailbox in the tenant could be impersonated, because the app has no path to a mailbox at all. The ISO-Outbox list plus the flow run history are the mail audit trail.

Power Automate flows
The outbox-send flow and the three nightly housekeeping flows in Chapter 11 are owned by the iso-noreply mailbox account, not a person, so they survive employee turnover. The outbox flow's mailbox connection is the single point that holds send rights; the housekeeping flows read and write the tool's SharePoint lists. Keeping mail on a list-plus-flow pattern avoids granting the app any mailbox permission.

Evidence upload endpoint

The same app exposes an evidence-upload endpoint. No end user holds Add rights on the Evidence library — the SPFx front-end streams the file here and the app performs the write as its own identity. Request: question id, file name, file bytes (base64), optional ISDocType.

  1. Authenticate & authorise the caller. Verify the caller is the question’s ISCurrentAssignee or a member of ISO - Core Team. Reject otherwise.
  2. Resolve the area. From the item’s ISStandardSlug and clause area, derive the permission-area folder for the question’s list.
  3. Locate the area folder. Verify the permission-area folder exists — the 11 area folders and their Matrix C ACLs are provisioned once by the permission-provisioning script. The endpoint does not create folders; it rejects the upload with a clear error if the area folder is missing.
  4. Upload via SharePoint REST. POST .../GetFolderByServerRelativeUrl('…')/Files/add(...) with the file bytes, then a MERGE on the new file's ListItemAllFields to stamp the metadata. (Chunked upload via Files/startupload for very large files is a documented follow-up.)
  5. Stamp metadata & return. Set ISStandardSlug, ISLinkedQuestionId, ISDocumentOwner (the caller), ISEvidenceArea, ISDocType; return the ServerRelativeUrl and a filename receipt.

This endpoint is independent of the reassignment transaction — an upload failure never rolls back a reassignment, and vice versa.

One carousel, not a form

Chapter 15The Certification Lifecycle

Chapters 1–14 describe how the tool captures a point-in-time snapshot of the ISMS: 748 question answers, the evidence library, the reassignment workflow. But an ISO certification is not a one-off — it must be renewed on a fixed three-year cycle, and the standard’s own clauses 9.2, 9.3 and 10.2 are recurring activities, not static descriptions. This chapter adds the operational layer that models time: the certificate cycle, every audit as a dated event, the running corrective-action register, and the management-review history — plus the reminder engine that keeps the calendar honest.

The three-year cycle

Accredited certification follows a fixed rhythm. The tool encodes it so the “where are we?” question always has an answer.

Cycle year External audit What the tool tracks
Year 0 Initial certification — Stage 1 (readiness) then Stage 2 (full audit) Two ISO-AuditEvents rows (Stage1, Stage2); a new ISO-Certifications row on success
Year 1 Surveillance audit (partial scope, sampled) One Surveillance audit event; the internal audit + management review that precede it
Year 2 Surveillance audit (partial scope, sampled) As year 1
Year 3 Recertification audit (full scope — the whole ISMS re-assessed) One Recertification audit event; on success the cycle restarts and ISCurrentCycleStart / ISExpiryDate advance

Every year, regardless of which external audit is due, the organization must run its own internal audit (clause 9.2) and hold a management review (clause 9.3) — both before the external audit, so findings and corrective actions are visible to the auditor. The certificate itself is valid for three years; the recertification audit must complete before ISExpiryDate.

The corrective-action lifecycle

A finding — whether raised by an internal audit, an external auditor, or ad hoc — is not closed by deleting it. It moves through a tracked state machine, and the ISO-Findings row carries the whole chain: root cause, the corrective action, an assignee, a due date, who verified it, and when it closed.

Status Meaning
OpenRaised; root cause and corrective action not yet agreed.
InProgressCorrective action under way; the assignee owns it.
AwaitingVerificationAction complete; awaiting an independent check that it was effective.
ClosedVerified effective. ISClosedDate and ISVerifiedBy are stamped automatically; closure requires a Core Team or Internal Audit member.

A finding may reference the audit that raised it (ISAuditEventId) and the catalog question it ties back to (ISRelatedQuestionId), so the auditor can trace a nonconformity straight to the ISMS content it concerns.

Chapter 16The Readiness Dashboard

The question carousel is built for doing the work — one focused question at a time. It is deliberately bad at answering the question a project sponsor actually asks: “how close are we?” The Readiness Dashboard is the answer. It is a read-only top-level view, reached from the Readiness toolbar button, that rolls the 748-answer catalog up into the three numbers a company chasing certification keeps asking for: how ready, what is left, and who owns the gap.

Scope-aware counting

Every tally on the dashboard respects the catalog’s appliesIf logic. Persistence — IsoListField now round-trips

Chapter 20Approval Workflow

ISO/IEC 27001:2022 clause 7.5.2 c) mandates “review and approval for suitability and adequacy” of documented information, and Annex A.5.1 requires top-management approval of the Information Security Policy specifically. Auditors expect a separate approver from the author and a trail of who approved or rejected and when. The wizard models this per-answer, because each evidence: true question in the catalog corresponds to exactly one controlled artefact.

States and transitions

Each answer carries an ISStatus column with three values: Draft, Submitted, and Approved. Rejection is an event, not a status — see below.

  • Draft — author edits freely. Default on first save.
  • Submitted — answer is locked from edits until either approved or rejected. The approver for the question's tier sees the row in the Readiness Approvals tab.
  • Approved — answer is locked; a green badge appears on the card and on the SoA/Risk Register row. Editing an Approved answer drops the row back to Draft and clears ISApprovedBy/ISApprovedAt; auditors see the prior approval in history.

Rejection is written to a separate ISRejectionHistory note column holding a JSON array of {RejectedBy, RejectedAt, Comment} records, and the row reverts to Draft so the author can revise. Keeping rejections out of the status enum keeps the state machine small while still satisfying the audit-trail requirements of clause 7.5.3 (control of documented information) and 9.2 (internal audit).

22.4 Out-of-scope documents follow the Statement of Applicability

The per-control applicability decisions (Chapter 17) do not only shape the SoA matrix — they decide which documents exist at all. When every Annex A control a document covers is marked Not applicable, the document is out of scope: the regeneration worker skips it, and if an earlier run already produced its PDF, that file is moved to the recycle bin so the library always mirrors the current applicability decisions. An organization that has descoped secure development (A.8.25–A.8.33), for example, will not find a Secure Development Policy in its library — and an auditor will not either. A document that covers a mix of applicable and excluded controls stays in scope and simply renders the excluded controls as such. Flipping a control back to Applicable and regenerating brings its documents back automatically. An unanswered applicability question counts as Applicable — excluding a control is always a deliberate, recorded decision, never a side effect of an unfinished questionnaire.

22.5 Tightening a heading after a review

All 1 042 catalog questions ship with a curated section heading that the tool will use when emitting a published document. If an auditor or reviewer suggests a different heading (“Policy intent” instead of “Purpose”, say), the change is captured in a small overrides file alongside the catalog. Re-running the tool’s generator and re-emitting the document picks up the new heading immediately — no answer has to be re-captured, no list schema changes, no SharePoint redeploy. The change is purely how the existing answer is presented.

In short
The tool gives you both the working draft your team needs and the controlled document your auditor wants — from the same answers, with no double entry. Status decides which one you get.

23.2 Saving — PDFs regenerate only when something changed

Save settings runs three stages and reports each in the status bar at the foot of the dialog:

  • Any staged permission changes from the Permissions tab are committed to the SharePoint groups.
  • The organization profile is written back to ISO-OrgProfile — but only if a field actually changed. An untouched profile is not rewritten.
  • Because the profile is printed onto every generated document, a changed profile triggers the server-side regeneration of the whole PDF library. The status names what changed — for example “FooterText changed — regenerating PDFs…” — and streams progress until the run completes.

If nothing changed, the status reads “Saved — organization settings unchanged, PDFs not regenerated” and the document library is left exactly as it was. Saving twice in a row is therefore always safe: the second save is a no-op, not a half-hour regeneration.

Forcing a regeneration
The Regenerate all PDFs button on the dialog footer re-renders every governance document with the current profile without requiring an edit. Use it after an interrupted regeneration run, or whenever you want to be certain the library reflects the latest answers and settings.

23.3 Permissions — the sixteen groups

The Permissions tab embeds the full permission-setup screen (Chapter 7): the sixteen SharePoint security groups arranged by sensitivity tier, live membership editing per group, and four exposure counters showing how many distinct people can read risk-assessment answers, incident-management answers and control-status answers.

The Grant full access (super-user) shortcut at the top stages one person into every internal group in a single action — pick the person, click Grant full access, review the staged cards, then save. Two groups are deliberately excluded: the time-boxed External Auditor (Read-only) group, which is reserved for a certification-body account, and the auto-managed Question Assignees bucket, whose membership is driven by question reassignment (Chapter 10).

The tool includes a built-in AI assistant that helps you write and check the content of your governance documents. To use it well it helps to remember how this tool builds a document: a Policy, Procedure, Register or Statement of Applicability is generated from the answers to the catalog questions mapped to it. So “producing a document” really means getting those answers written well and consistently, then letting Save & Regen render the controlled-document PDF. The assistant’s job is to help you draft those answers, keep them consistent across the whole library, and turn ideas into diagrams.

24.3 The core drafting loop

Working a document question by question, the most effective rhythm is read → draft → review → refine → diagram → save:

  1. It reads the context first. The assistant automatically receives the focused question’s clause reference, official guidance, answer hint, remediation steps, expected answer type and list columns — plus your organization profile (legal name, contacts, default owner, confidentiality, review cadence). A prompt such as “Draft an answer for this question for our organisation” therefore produces clause-aware, organisation-specific text rather than generic boilerplate.
  2. It drafts, then shows a preview to apply. The proposed answer opens in a preview dialog — formatted text and any diagrams shown exactly as they will look in the document (not raw markup) — with Apply / Cancel. Nothing lands in the answer until you click Apply, and you can still Undo last AI edit afterwards.
  3. Review what it knows versus what it asserts. Ask it to ground claims in real data — “Before drafting, check what we already say about access control” — so it reuses your actual decisions instead of inventing them.
  4. Refine in place. “Tighten this to half the length.” · “Add a sentence about annual review.” · “Replace the third paragraph with a RACI summary.” It can replace or append to the current answer.
  5. Insert diagrams as part of the answer (Section 24.4).
  6. Save & Regen when the answers look right — that is the step that renders the PDF. The assistant writes the answer content; you trigger the save and remain accountable for it.
A realistic session
Walk the carousel question by question: ask the assistant to draft each answer, confirm and refine, drop in a diagram or two, then Save & Regen once at the end. Some example openers: “Draft a concise answer covering points a–d of this clause”, “Write this as a policy statement in our house style — short paragraphs, no jargon”, “This question expects a list — propose the first five rows for the columns shown”.

24.4 Producing diagrams

Diagrams are first-class document content — just describe what you want and the assistant inserts a proper, double-click-editable diagram into the answer, in the same format the toolbar produces, so it renders correctly in the final PDF:

  • “Insert a flowchart of our incident-response process: detect → triage → contain → eradicate → recover → review.”
  • “Add a RACI matrix for the data-classification roles.”
  • “Draw a data-flow diagram: customer → web app → database, marking the trust boundary.”

Good candidates are process flows (procedures), RACI charts (roles and responsibilities clauses), network and data-flow sketches (Annex A technical controls) and the ISMS scope boundary (clause 4.3). You can double-click any AI-inserted diagram afterwards to edit it by hand.

24.6 Getting the best results

  • Be explicit about scope and style — “covering a–d”, “policy tone”, “≤150 words”, “as a list”.
  • Tell it to read before asserting — “check our existing answers first” keeps it grounded in your real ISMS, not a generic template.
  • Iterate in small confirmed steps rather than one giant write — easier to review and accept.
  • Use the rail to decide what to write, the editor to write it.
  • Treat diagrams as describable — give the nodes and flow in plain English and let it produce the diagram.

The assistant drafts; an auditor judges your document. Every answer it writes is advisory — read it critically before Save & Regen. It is a drafting and consistency aid, not a certification authority, and it never touches approval state: approval and the separation-of-duties rule (the last editor cannot approve the same document) are unchanged.

  • Scoped reads, not omniscience. To stay fast the assistant reads in slices (per document, per clause, by search); very large results are truncated with a marker. If it says a result was truncated, ask a narrower question rather than assuming it saw everything.
  • Shared and visible. The key and conversation history live on the site and are visible to everyone with access — do not paste secrets into the chat.
