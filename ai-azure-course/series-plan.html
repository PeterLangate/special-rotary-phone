Chapter 1Manage Azure by chatting with Claude Code

It is possible to manage Microsoft Azure just by chatting with Claude Code in Visual Studio Code — doing the work by conversation rather than by clicking through the Azure portal. We still open the portal often, to see the results of what Claude did. This series shows how.

Claude Code is more than a tool. Through the series it works like a co-worker you can delegate to and ask for advice: you say what you want in plain words, and Claude proposes the command, explains the result and suggests what to do next. It is still an AI, though, so you check and rein in what it produces — which is what the read, change and delete mindset below is for.

It starts from nothing installed and builds up to creating, changing, investigating and governing every resource in a subscription by conversation, one short task at a time — and every change is documented as it is made.

The presenter works with the Claude Code extension in Visual Studio Code, so every demo stays inside one editor. The first episode installs everything and connects to Azure; from there, Claude proposes each command and the presenter reads it before it runs.

Read, change, delete

The safety mindset runs through every episode. Azure tasks come in three kinds that carry different risk:

  • Read — listing resources, reading logs, checking costs. These are safe, so Claude can run them freely.
  • Change — creating a resource, resizing a virtual machine, editing a configuration. Read Claude's proposed command first, then approve it.
  • Delete — removing a resource or a resource group. Always read the command, and confirm that it names only what you mean to remove.
Always ask before deleting. A rule in the project CLAUDE.md file tells Claude to describe what it will remove and wait for approval first.

Chapter 2Before you start

The series is a fresh start. It assumes nothing is installed and nobody has touched Azure yet — the very first episode sets everything up and connects to a subscription, so anyone can follow from zero.

All a viewer needs before Episode 1 is short:

  • A machine with Visual Studio Code — Windows or Mac. Visual Studio Code is free, and every demo happens inside it.
  • A Claude Pro subscription — about USD 20 a month. This is what powers Claude Code, the assistant that does the work.
  • An Azure subscription — a paid one or a free trial. A Claude plan and Azure access are the two things you bring; the series sets up the rest.

Everything else is installed and configured on screen in Episode 1, so the series never depends on any earlier video.

Episode 1 sets it all up

The first episode installs Claude Code and the Visual Studio Code extension, installs the Azure CLI and Azure PowerShell, and signs in to Azure with az login. By the end of it the viewer has a working setup and has already read, changed and deleted a resource by chatting — so the later episodes can go straight to real management.

Keep the extension framing, and lean on CLAUDE.md

The demos stay in the Visual Studio Code extension, not the raw terminal, so there is one editor to learn. Episode 1 also creates the CLAUDE.md memory file, which becomes the natural place to store subscription IDs, resource-naming conventions, and guardrails such as "always ask before deleting". That recurring thread is unique to this series, so every later episode leans on it.

Chapter 3The Microsoft surfaces Claude drives

To manage Azure with Claude and Microsoft only, Claude drives Microsoft's own command surfaces. Four of them form the backbone of the series, and all four are first-party.

SurfaceWhat it isWhere the series uses it
Azure CLI
az		 The cross-platform command line for Azure — the workhorse. Claude runs it in the terminal. Most everyday reading and changing tasks.
Azure PowerShell
Az module		 The same operations expressed in PowerShell. Shown as the natural choice for the PowerShell-oriented viewer.
Azure MCP Server Microsoft's official MCP server. It gives Claude structured Azure tools instead of raw commands. The automation episode, compared against raw az.
Bicep Microsoft-native infrastructure-as-code. Claude writes the file, you deploy it. The infrastructure-as-code episodes.

Show all three command surfaces

Azure CLI, Azure PowerShell and the Azure MCP Server reach the same subscription in different ways. The series shows each of them at least once, so viewers can pick the one that suits how they already work. Claude reads an Azure error message and corrects itself on any of the three — a strong point in favour of chatting over clicking in the portal.

The series stays Claude + Microsoft only — Bicep for infrastructure as code, and Microsoft's official Azure MCP Server, not a community one.

Chapter 5Threads through every episode

Some ideas are too important for a single episode. The strongest is the learning loop — the way the course teaches. It runs through every hands-on demo, and the supporting threads below run alongside it.

The learning loop — the course spine

The audience is not shown a finished answer to copy. They watch the presenter set a goal, let Claude attempt it, read the error when it slips, and save the pattern as a skill once it proves reliable.

1 · Goal

Set a goal

Say what you want in plain words, and let Claude restate it.

2 · Try

Let Claude try

Read the proposed command, then let it run — mistakes allowed.

3 · Learn

Learn from the error

Claude reads the Azure error, explains it, and self-corrects.

4 · Skill

Save what works

Capture the proven pattern as a skill Claude reuses next time.

Alongside the loop, one stance and six threads recur:

A co-worker, not just a tool

Claude Code is treated as a colleague you delegate to and ask for advice — it proposes commands, explains Azure's replies and suggests next steps — while you stay in charge. Because it is still an AI, you check and rein in its output; the six threads below are how.

Rely on Claude, but verify

Keep prompts short and conversational and let Claude work out the details — then check the result. Verify by hand and in the portal, and automatically: have Claude write end-to-end tests (Chapter 6) and let a critical sub-agent review the work.

Authentication and identity

az login, the right subscription and tenant, and service principals or managed identity for unattended runs.

Review before running

Read Claude's proposed command before approving, and use what-if or --dry-run where Azure supports it.

Read versus change

Keep safe reading and querying clearly apart from create, delete and modify tasks — the split the whole series is built on.

Cost, clean-up and RBAC

Clean up what you create so nothing is left billing, and set least-privilege access before any automation episode.

Document every change

Every change is written down, not just made. The command is shown before it runs, resources are tagged with their purpose, and any notable change is noted so the subscription's history stays readable.

The loop is the point. Mistakes are where the learning happens, and each saved skill makes the next episode start stronger.

Chapter 6End-to-end testing with Playwright

The series runs on one rule: rely on Claude, but verify. Keep the prompt short and let Claude work out the details — then prove the result is right, by hand and automatically. For anything with a web front end, that automatic proof is an end-to-end test written with Playwright.

Why an end-to-end test

Azure reporting a deployment as Succeeded only means the resource was created. It does not mean a visitor can open the site, sign in and use it. An end-to-end (E2E) test drives a real browser through those same steps, so it checks the experience, not just the resource. Once written it stays as a safety net: run it again after the next change and it catches whatever broke.

First-party, like the rest

Playwright is Microsoft's own open-source browser-automation tool, so it fits the Claude + Microsoft only rule. One test drives Chromium, Firefox and WebKit, and it waits for the page on its own instead of guessing with sleeps.

Claude writes it

You describe the flow in plain words; Claude writes the test — or records a first draft with npx playwright codegen — runs it with npx playwright test, reads any failure and fixes it. The same learning loop as everywhere else in the series.

The verify loop

1 · Ask

Describe the flow

"Open the site, check the home page loads and sign-in works."

2 · Write

Claude writes the test

A Playwright test against the deployed URL, then run from the terminal.

3 · Check

Verify two ways

You spot-check by hand and in the portal; the test proves the flow automatically.

4 · Review

A critical sub-agent

A second Claude reviews the test and the code, hunting for what the first one missed.

Two kinds of proof. The portal shows the state of a resource; a Playwright test proves the experience still works. Rely on Claude to build both the app and its test — then trust the green test, not just the word "Succeeded".

Appendix: Definitions

The series assumes no prior Azure knowledge. This appendix defines the tools and concepts it uses, in plain language. Terms are listed alphabetically; a word shown in italics has its own entry.

TermWhat it is
AKS (Azure Kubernetes Service)A managed Azure service that runs containers grouped into a cluster, and handles scaling and restarting them for you.
App ServiceAn Azure service that hosts a website or web API without you managing the server underneath — a PaaS service.
ARM templateAn Azure Resource Manager file (in JSON) that lists resources to create. Bicep is a friendlier language that turns into an ARM template.
AzureMicrosoft's cloud platform: you rent computing, storage and networking instead of running your own servers.
Azure AI servicesAzure's services for adding AI to apps, including Azure OpenAI (models such as GPT) and AI Foundry (a workspace for building AI solutions).
Azure CLI (az)Microsoft's cross-platform command line for Azure; every command begins with az. Claude runs these for you.
Azure Cost ManagementThe part of Azure that shows what resources cost and where the spend goes.
Azure FunctionsA "serverless" service that runs a small piece of code on demand (say, when a file arrives), without you managing a server.
Azure MCP ServerMicrosoft's official MCP server that gives Claude ready-made Azure tools instead of raw az commands.
